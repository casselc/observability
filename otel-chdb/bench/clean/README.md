# Clean benchmark suite: the sizing calculator's constants on an idle box

Every earlier number behind `central-sizing.html` was measured on a shared
4-vCPU box at load 1–3. This suite re-measures them with the box idle and gated
(load ≤ 0.45 at each run's start, CPU steal checked per run), at least 5
repetitions where a repetition is meaningful, client and server pinned to
separate CPUs. Every clean number sits next to the earlier loaded-box one.

### Constants that changed by more than 15%

- **`usRow`, insert µs per span or log: 5 → 3.43 [2.87–3.96] (−31%).** All-in
  CPU of one-object, 10k-row statements (the calculator charges spans and logs
  no separate fixed cost, at its 10k rows per object). The marginal per-row
  slope is 2.21 [1.88–2.38]; at the consumer's default 32 objects per
  statement the all-in cost is 2.55 (traces) and 2.18 (logs) µs/row.
- **`usPointA`, insert µs per ClickStack-table point: 7.85 → 4.47 [3.65–4.80]
  (−43%).** Caveat: not the same objects. The earlier 7.85 came from the Go
  parquetgo contrib objects (metrics-layout, 20k-point mixed batches); the clean
  runs insert the Rust edge's `clickstack_tables` objects of the same fleet
  generator. The series-layout equivalent (`usPointB`) moved by only +2%, so
  load explains little of this; treat the A drop as partly an object/encoder
  difference.
- **`mergePointB`, merge µs per series-layout point: 6.5 → 4.1 (−36%)** and
  **`mergePointA`, merge µs per ClickStack point: 30 → 19.4 (−35%)**, both
  projected to 10⁴ parts per daily partition. The clean runs reached 1,500–2,100
  parts for number, histogram and summary points (the earlier 100k runs:
  118–588), so the slope is their own, not borrowed from 10k-row runs.

Unchanged within 15%: `usPointB` (+2%), `fixedMs` (−10%), `mergeRow` (−9%),
stored bytes `bPointB` (+6%), `bPointA` (+1%), `bSeries` (−4%), and every edge
constant (−11% … +13%). `bSpan` and `bLog` are the calculator's estimates for
real telemetry (80 / 60 B), not measurements. The synthetic data stores 39 B per
span with random ids, 9.6 with testgen ids, and 19 B per log (block 4); these
are not proposed as replacements. `rollUs*`, `rollWin*` and the Parquet-byte
constants were not in scope.

it falls about a quarter (357 → 263) and loses a shard (6 → 5). Storage does
not move (±1%), and neither does edge CPU (±5%). The layout B vs A conclusion
holds: B needs about a third of A's central CPU.

## Method and environment evidence

**Box.** Intel Xeon @ 2.80 GHz, 4 vCPUs, kernel 6.18.44 (`lscpu.txt`; a header
line with model, nproc, kernel and free disk opens and closes every block's
`env.jsonl`). ClickHouse 26.10.1.618 for both the shared and the private server.
Nothing else ran: each block's services were started alone (`driver.sh`,
`lib/services.sh`).

**Gating and evidence.** `lib/env.sh` snapshots `/proc/loadavg` and the
aggregate `/proc/stat` cpu line (steal included) before and after every run
(`begin`/`finish`) and around every measured process. Each run waits until the
1-minute load is ≤ 0.45, so no run starts above 0.5. `lib/envlog.py` pairs the
snapshots and flags steal > 2% or load at start > 0.5.

| block | runs (repetitions) | load at start, max | steal per run, median / max | flagged |
|---|---|---|---|---|
| 1 edge encode | 17 gated repetitions (550 processes) | 0.45 | 0.30% / 0.45% | 2 processes > 2% steal, re-run (`block1/rerun.sh`) |
| 2 central insert | 20 (5 × 4 configurations) | 0.45 | 0.32% / 0.48% | 0 |
| 3 merges | 10 (one per table) | 0.45 | 0.29% / 0.39% | 0 |
| 4 stored bytes | 2 passes | 0.45 | 0.33% | 0 |
| 5 consumer | 30 (5 × 6 configurations) | 0.45 | 0.36% / 0.58% | 0 |

**Restarts.** The container restarts about hourly and kills every process.
Every block script skips runs that already have a result; `driver.sh` starts
the services each block needs and reruns the rest; `PROGRESS.md` is generated
from the result files. One restart fell inside block 2 (after repetition 4's
first run). Repetitions 4–5 ran on the new boot and came out 10–15% cheaper per
row than repetitions 1–3 (e.g. traces 2.18 and 2.02 against 2.29–2.53 µs/row),
with steal and load no different. That is boot-to-boot host variation, and the
reported ranges include it.

### Block 1: edge encode and publish CPU (`block1/`)

otap-rs's own bench scripts, unchanged (`bench.sh`, `metrics_bench.sh`,
`series_bench.sh`), 5 interleaved repetitions. The measured process is pinned to
CPUs 0-1; the driver and SeaweedFS to CPUs 2-3. Full table: `block1/results.md`
(CPU ms per 10k rows/points, median [min–max], earlier otap-rs and parquetgo
results beside it).

- Rust encoders (spans, logs, per-type metrics): −2% … −23%. Go parquet-go spans
  and logs: −6% … −11%. Go per-type metrics: −19% … −34% against the otap-rs-era numbers, but only −1% …
  −10% against the parquetgo results the calculator used.
- **Four rows are slower on the clean box:** the Rust `series_table` and
  `clickstack_tables` metrics paths, +18% … +33% (`series-fleet` 20.8 vs 17.6,
  `rust-pipeline-clickstack_tables` 62.0 vs 46.5 ms per 10k). An idle box cannot
  make a process slower, so this is a code or data change since the earlier
  run, not load. It is why `edgeRsPointA` rises (+13% over the calculator, +33%
  over its like-for-like), and it merits a look.

### Block 3: merge CPU per row (`block3/`)

bench/merges' method (`merges.py`, copied with the changes listed in its
docstring). One table per run, INSERT … SELECT FROM s3() shaped as the consumer
sends them (single block, squashed, dedup token, fence), at 100k rows per
statement, 3 concurrent workers at a fixed rate. The private server is on CPUs
1-3, the driver and SeaweedFS on CPU 0. Per-merge CPU comes from `part_log`
(`OSCPUVirtualTimeMicroseconds`), per-insert CPU from `query_log`
(`results/<run>/*.jsonl.gz`); `analyze.py` → `analyze.md`, `fit.py` → `fits.txt`,
`proj_clean.py` → `results.md` and `proj_clean.json`. Cross-check: `part_log`
merge CPU is 0.95–0.99 of the merge threads' `/proc` CPU in 9 of 10 runs (0.80
for exp. histograms, whose drain was cut short at the disk floor).

Projection (bench/merges `proj.py`): M(N) = M(N_end) + b·ln(N/N_end)·c. Here b
is the run's own slope of rewrites per row against ln N, fitted over N ≥ 50
parts, and c is its µs per row read in merges ≥ 16× the insert size. The other
estimate in brackets is fit.py's direct fit M = a + b·ln N, or, for a run that
borrows a slope, its own short-range slope.

- **Parts reached.** The 1,000–2,000-parts target was met for testgen-id traces
  (1,066), number (2,100), histogram (1,496) and summary points (1,800). It was
  **not** met for the wide tables. With free disk held ≥ 2.5 GB, the data plus a
  top-level merge's output (written while its sources still exist) must fit in
  about 2 GB. That stopped random-id traces (39 B/row) at 161 parts, logs at
  536, exp. histograms at 458, ClickStack sum at 491 and histogram at 314 (the
  earlier 100k runs: 96–519). Random-id traces therefore borrow the slope of
  the testgen-id traces run (1.37 rewrites per decade); the others have
  ≥ 300 parts and use their own slopes. The first random-id traces attempt also
  hit the floor at 161 parts because outdated parts were kept 30–40 s
  (1.5 GB of them); `old_parts_lifetime` 5 s with a 1–2 s cleanup (disk only)
  did not help, because the limit is the merge output itself.
- **Compared with the earlier projections** (`../merges/results/projection.md`,
  100k rows at 10⁴ parts): spans and logs −9% … −31%; series-layout points
  −32% … −56%; ClickStack histogram −23%. Merge ÷ insert at 10⁴ parts is
  2.2–4.4×, close to the earlier 2.2–5.0×, because insert got cheaper too.
- The merge pool is replayed (24 or 50 rounds, time-shifted), as in the earlier
  runs, so the comparison is like-for-like. Block 4 shows that replay halves
  the counters' stored bytes, so series-layout merge CPU may be slightly
  optimistic in absolute terms.

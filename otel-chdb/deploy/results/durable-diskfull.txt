# Durable buffer full: backpressure vs drop_oldest vs a full filesystem
# deploy/scripts/diskfull.sh, 2026-09-26, otap-s3pq release build (upstream
# 5db8358), configs/edge-durable.yaml with the cap/policy below. S3 is a
# closed port while two senders stream 32 distinct 10k-span (~6 MB) and 32
# distinct 10k-log (~4.5 MB) requests for 60 s, resending on 503; SIGKILL;
# restart on the same buffer with S3 up; 25 s drain. "Committed whole" maps
# each object's rows back to the request that carried them.
#
# Findings:
# - backpressure: at the cap the receiver answers 503 (retryable) "storage
#   at capacity"; every acked request is committed after the restart. 0 lost.
# - drop_oldest: every request is acked (the client is told OK), and the
#   oldest segments are deleted to make room: 47 of 64 acked requests never
#   reached S3. Silent loss; never use it.
# - a full filesystem before the cap (the cap set above the volume): ingest
#   fails retryably (503 "wal io error"), nothing acked is deleted, but the
#   restart cannot replay the WAL (it needs room to write a segment), the
#   engine fails 5 times and the process exits; in Kubernetes a crash loop.
#   After the filesystem is grown (a PVC expansion) the next start commits
#   every acked request. Stuck, not lost; the cure is a cap well below the
#   volume, so the cap, not ENOSPC, is what pushes back.
# - the engine refuses a cap under 192 MiB per core (WAL max 128 MiB + 2
#   segments of 32 MiB); the soft cap is the cap minus one segment.
